# Responses API

TabbyAPI exposes `POST /v1/responses` alongside Chat Completions. It implements a
**stateless subset** of the OpenAI Responses protocol for local models and configurable
agent clients. Use the same base URL and API key as the other OpenAI endpoints.
The loaded model still needs a chat template and, for tools, a supported tool format.

## Quick start

```python
from openai import OpenAI

client = OpenAI(base_url="http://localhost:5000/v1", api_key="YOUR_TABBY_API_KEY")
response = client.responses.create(
    model="YOUR_LOADED_MODEL",
    input="Explain how a hash table works.",
    instructions="Be concise.",
    max_output_tokens=512,
    store=False,
)
print(response.output_text)
```

For streaming, pass `stream=True` and consume `response.output_text.delta` events.
Check the terminal event: `response.completed`, `response.incomplete`, or
`response.failed`. There is no Chat Completions `[DONE]` sentinel. Early request errors
use an OpenAI-shaped HTTP error; generation errors after streaming begins use
`response.failed`. Non-streaming generation failures return a Response with
`status: "failed"` and `error`, so clients must inspect status.

## Supported parameters

| Capability | Behavior |
| --- | --- |
| `input` | String, system/developer/user/assistant messages, assistant output messages, function/custom calls and their results |
| `instructions` | Prepended to the model's chat context; developer roles use the existing system-role normalization |
| `model` | Existing model selection and inline-loading policy |
| `stream` | Named SSE events, ordered output items, stable IDs, increasing sequence numbers |
| `max_output_tokens`, `temperature`, `top_p` | Mapped to existing sampling settings; output limit includes reasoning and tool generation |
| `tools` | Function tools and custom text/Lark tools executed by the client |
| `tool_choice` | `auto`, `none`, `required`, named function/custom tool, or `allowed_tools` |
| `parallel_tool_calls` | Multiple generated calls allowed by default; `false` rejects multiple calls |
| `text.format` | `text`, `json_object`, or named `json_schema`; cannot combine JSON formats with active tools |
| `reasoning.effort`, `text.verbosity` | Forwarded as template hints; effects depend on model/template and server overrides |
| `reasoning.summary` | Only absent, null, or `none`; generated reasoning stays internal |
| Images | HTTP(S)/data URLs on vision models, with `detail: "auto"` only |
| `metadata` | Echoed on the Response; no history is persisted |
| `store`, `background` | Must be false; **`store` defaults to false**, unlike OpenAI |
| `truncation` | Only `disabled`; oversized contexts fail before SSE starts |
| `include` | Empty or `reasoning.encrypted_content`; no encrypted content is produced because no reasoning items are returned |
| `prompt_cache_key`, `client_metadata` | Accepted advisory fields for agent clients; no routing or persistence effects, KV caching remains backend-managed |

Unknown fields and unsupported behavior-changing options are rejected. Request validation
errors return HTTP 400 with `error.message`, `error.type`, `error.param`, and `error.code`.
Image resolution controls, files, audio/video, output logprobs, hosted tools, tool namespaces,
background jobs, response storage/retrieval/deletion, `previous_response_id`, Conversations,
WebSockets, and remote compaction are not implemented.

Usage reports backend input/output totals and cached input tokens. The optional
`output_tokens_details` object is omitted because the backend does not supply exact
reasoning-token attribution. It is not populated with invented zeros.

## Tool round trips

Responses function definitions are flat:

```python
tools = [{
    "type": "function",
    "name": "read_file",
    "description": "Read a file from the client workspace.",
    "parameters": {
        "type": "object",
        "properties": {"path": {"type": "string"}},
        "required": ["path"],
        "additionalProperties": False,
    },
    "strict": True,
}]
inputs = [{"role": "user", "content": "Read README.md"}]
response = client.responses.create(model="YOUR_LOADED_MODEL", input=inputs, tools=tools)
inputs.extend(item.model_dump(exclude_none=True) for item in response.output)
# Execute validated calls in your client, then append one result per call:
# inputs.append({"type": "function_call_output", "call_id": call.call_id, "output": result})
# response = client.responses.create(model="YOUR_LOADED_MODEL", input=inputs, tools=tools)
```

Send the full history every turn. Each replayed call needs exactly one matching result;
parallel results may arrive in a different order. Preserve `call_id` and distinguish it
from the output item's `id`. Replayed calls do not require the tool to remain declared.

Custom tools use `type: "custom"` and optional `format: {"type": "text"}` or
`format: {"type": "grammar", "syntax": "lark", "definition": "..."}`. Internally, they
are presented to the model as functions with one string `input` argument. The decoded
string is returned as `custom_tool_call.input`; submit a `custom_tool_call_output`
with the same call ID. Grammar text is included in the tool description and validated
with Lark before the call is returned. Only single bundled `common` terminal imports
are supported; local imports and regex grammars are rejected.

Function `strict:true` requires every object property to be required and
`additionalProperties:false`. With strict omitted, compatible schemas are normalized;
incompatible ones fall back to `strict:false`, reflected in the returned tool definition.
Explicit unsupported strict constraints (`format`, `patternProperties`,
`unevaluatedProperties`, `$dynamicRef`) are rejected. External schema references are
rejected. Strict validation happens **after generation**; it does not guarantee the
model will successfully produce a call on every request.

Tool calls are buffered, parsed, and validated before executable calls are emitted.
Text preceding the first call streams immediately; later text is buffered to preserve
item order. Invalid or undeclared calls, violated schemas/grammars, and disallowed call
counts fail the response without releasing any calls. There are no automatic retries.
A token-limit stop returns `incomplete` and withholds pending tool calls. Existing
model-specific parser limitations still apply; Responses uses stricter completeness
checks than Chat Completions.

## Codex configuration and qualification

A tested configuration for a custom provider is:

```toml
model = "YOUR_LOADED_MODEL"
model_provider = "tabby"
model_reasoning_summary = "none"
model_supports_reasoning_summaries = false
web_search = "disabled"

[model_providers.tabby]
name = "TabbyAPI"
base_url = "http://localhost:5000/v1"
wire_api = "responses"
env_key = "TABBY_API_KEY"
requires_openai_auth = false
supports_websockets = false

[features]
multi_agent = false
apps = false
skill_search = false
tool_suggest = false
```

These settings disable unsupported hosted/namespace capabilities. Configure the model's
actual context window separately and use a model trained for tools. This is not a claim
that all Codex features or ordinary ChatGPT desktop chats support this provider.

Protocol qualification on 2026-09-16:

| Client | Version | Result with deterministic backend |
| --- | --- | --- |
| Python OpenAI SDK | 3.14.1 | JSON, SSE, function/custom tool replay |
| JavaScript OpenAI SDK | 6.32.0 | JSON, SSE, function/custom tool replay |
| Codex CLI | 0.154.0-alpha.6.2 | Read disposable file, edit through shell tool, consume results, final answer |

**Live model quality and GPU execution have not been qualified.** The development
checkout had no model weights or ExLlamaV3 runtime. The mock tests exercise the real
HTTP endpoint, adapters, parser, and serializers; they cannot measure model reliability.
ChatGPT desktop compatibility is unverified.

To reproduce protocol tests after installing project dependencies:

```bash
pip install -e . -r tests/requirements-responses.txt
python -m pytest tests -q
npm ci --prefix tests/responses_clients
python tests/responses_clients/run.py
# Requires the qualified Codex build on PATH; edits only a disposable fixture:
python tests/responses_clients/run.py --codex
```

Before qualifying a real deployment, repeat text, function/custom tool, JSON-schema,
vision, token-limit, and disconnect tests on the loaded model. In particular, measure
custom patch-tool success: translating raw text through a JSON string can be less
reliable than a model trained for native custom tools.
