## Performance Tuning: Multi-GPU with CPU MoE Offload

This page collects what was measured while tuning large MoE models (DeepSeek-V4.1-Flash and
GLM-5.3-Flash) on a mixed multi-GPU machine with part of each MoE layer offloaded to the CPU.
The general guidance applies to similar setups; the numbers at the end are from one machine and
are there as a worked example, not as targets.

Measured on 2026-11-17 with ExLlamaV3 1.6.7 plus the pipelined prefill patch described below.

### Pipelined prefill with CPU offload (patched ExLlamaV3)

Stock ExLlamaV3 runs prefill as a pipeline across GPUs (each GPU works on a different chunk at
the same time), but it falls back to serial prefill whenever experts are offloaded to the CPU or
attention is pinned to one device (DeepSeek-V4 does this). The `ds-pipelined-prefill` branch of
the ExLlamaV3 fork at <https://github.com/duyyudus/exllamav3> lifts both restrictions. It is a
small patch on top of ExLlamaV3 1.6.7 (three files, about 180 lines). Measured gains over serial
prefill:

| Model | Prefill speedup |
|---|---|
| DeepSeek-V4.1-Flash (attention pinned to GPU 0, CPU offload) | about 1.25x to 1.5x |
| GLM-5.3-Flash 4.1bpw (CPU offload) | about 1.7x to 1.8x |

Models with neither CPU offload nor pinned attention take the stock code path unchanged.

Output was compared bit for bit against serial prefill (single requests, cached-prefix reuse,
checkpoint resume and two concurrent requests) on both models. Decode speed and VRAM use are
unchanged.

The patch only speeds up prefill while nothing else is decoding: the generator flushes the
pipeline before every decode step, so with several requests at once, a prompt that arrives while
another request is generating prefills at serial speed. That is correct, just not faster.

**Using the fork.** Clone the branch, then point `developer.exllamav3_path` at the clone in the
configs that should use it:

```sh
git clone -b ds-pipelined-prefill https://github.com/duyyudus/exllamav3 ~/git/exllamav3
```

```yaml
developer:
  exllamav3_path: ~/git/exllamav3
```

The same option is available on the command line as `--exllamav3-path ~/git/exllamav3`. Configs
without it use the installed package, so the patch is switched per config, and removing the line
switches it off. The startup log shows `Using exllamav3 from <path>` when it is active.

Only the Python package is loaded from the clone; the compiled extension still comes from the
installed ExLlamaV3 wheel, so no build is needed. That also means the clone must stay on the same
release as the installed wheel and must not change C++/CUDA code. After merging a newer upstream
release into the fork, update the installed wheel to the same version.

| Variable | Default | Effect |
|---|---|---|
| `EXL3_DS_PIPELINE` | `1` | `0` restores the stock rule (serial prefill with CPU offload) |
| `EXL3_DS_PIPELINE_DEPTH` | `2` | Chunks in flight. `3` gave about 3% more prefill for more VRAM on GPU 0 |
| `EXL3_DS_PIPELINE_MIN_ROWS` | `256` | Shorter chunks run serially |

### Environment variables

These cannot be set in `config.yml`; put them in front of the launch command.

| Variable | Recommended | Why |
|---|---|---|
| `CUDA_DEVICE_ORDER` | `PCI_BUS_ID` | Always, with mixed GPUs. See below |
| `EXL3_MOE_HOST_CORES` | `2` for DeepSeek, unset (1) for GLM | Physical cores reserved for the server process |
| `EXL3_MOE_STREAM_T` | unset | Leave the per-GPU automatic value |

**`CUDA_DEVICE_ORDER=PCI_BUS_ID`.** By default CUDA numbers GPUs fastest first, not in the order
`nvidia-smi` shows. `gpu_split` (and any autosplit) follows CUDA's numbering, so adding or
swapping a card can silently move the budgets to different GPUs. On the machine below, adding an
RTX 4090 made it GPU 0 ahead of the RTX PRO 5000, which would have given the 70 GB budget to
a 24 GB card. With `PCI_BUS_ID`, the numbering matches `nvidia-smi`.

**`EXL3_MOE_HOST_CORES`.** With CPU offload, ExLlamaV3 pins the server process to this many
physical cores (default 1, i.e. two logical CPUs) and gives the rest to the expert worker.
Pipelined prefill runs one host thread per GPU stage, and on DeepSeek one core was not enough:
with 2, prefill was 10% to 25% faster and decode unchanged. On GLM the same change made prefill
22% to 32% slower (decode about 8% faster); the reason is not known, so leave GLM at the
default. More than 2 gave nothing further. Keep `cpu_moe_threads` at or below physical cores
minus host cores (14 on a 16-core CPU with 2 host cores); with more worker threads, the host gets
fewer cores than requested. tabbyAPI sizes its torch thread cap from this variable automatically.

**`EXL3_MOE_STREAM_T`.** During prefill, CPU-held experts that enough tokens use are streamed to
the GPU and the rest are computed on the CPU. The engine picks this cut-off per GPU from its
measured link speed (about 8 on a Gen5 x8 link up to about 20 on a 3.8 GB/s link). Setting the
variable replaces that with one value for every GPU. Hand-tuned per-GPU values were at most 1% to
3% better on the current hardware, so it is not worth changing.

### Config settings

**`gpu_split`.** Budgets in GB per GPU, in `CUDA_DEVICE_ORDER=PCI_BUS_ID` order. Put the largest
card first: GPU 0 holds the first pipeline stage and, for DeepSeek, every layer's attention and
the n-gram layers. Moving layers off GPU 0 (smaller GPU 0 budget, more on other cards) was slower
in every layout tried. A budget of 70 on a 72 GB card peaked at about 71 GiB in use, leaving
roughly 0.6 GiB free. That is tight but stable.

**`cpu_moe_split_experts`.** Use the lowest value that loads. Fewer experts on the CPU means
less to stream per chunk, so prefill improves at every step down. Decode gains little, because
decode is limited mostly by host overhead. A value too low fails at load with
`Insufficient VRAM in split for model and cache`.

**`chunk_size`.** 4096 was 10% to 30% faster than 2048 for prefill, because streaming the CPU
experts costs about the same per chunk whatever its size. Larger chunks did not fit: at load the
engine reserves one full chunk's working memory on every GPU, so 6144 or 8192 left too little
room for the layers on 24 GB cards.

**`draft_mode: mtp`.** Faster decode on both models. `draft_num_tokens` empty for DeepSeek (its
drafter has a fixed block size), 2 for GLM.

**`max_batch_size`.** 1 for a single user. 2 works correctly with the patch, but the extra cache
needs VRAM that GPU 0 barely has on DeepSeek.

### Measured setups

Hardware: Ryzen 9 7950X (16 cores), 122 GB RAM, five GPUs. Each GPU's PCIe link decides how fast
CPU-held experts reach it during prefill.

| GPU (PCI order) | Card | Connection | Host to GPU |
|---|---|---|---|
| 0 | RTX PRO 5000 72 GB | CPU lanes, Gen5 x8 | 28.9 GB/s |
| 1 | RTX 4090 24 GB | CPU lanes, Gen4 x8 | 13.4 GB/s |
| 2 | RTX 3090 24 GB | chipset, Gen4 x4 | 6.4 GB/s |
| 3 | RTX 3090 24 GB | USB4 enclosure | 3.8 GB/s (3.3 when both USB4 cards are busy) |
| 4 | RTX 3090 24 GB | USB4 enclosure | 3.8 GB/s (3.3 when both USB4 cards are busy) |

Both configs below also set `developer.exllamav3_path` to the patched fork.

Benchmarks are uncached prompts of about 13K and 60K tokens, then three 500 to 600 token greedy
generations. During a long run the engine moves frequently used experts into spare VRAM, so
sustained prefill on repeated content climbed to about 1,400 T/s (13K) and 1,900 T/s (60K) on
GLM. Real, varied use lands between the cold numbers below and those.

#### DeepSeek-V4.1-Flash 2.68bpw

```yaml
gpu_split: [70,24,24,24,24]
cpu_moe_split_experts: 72
cpu_moe_threads: 14
chunk_size: 4096
draft_mode: mtp
```

```sh
CUDA_DEVICE_ORDER=PCI_BUS_ID EXL3_MOE_HOST_CORES=2 ./start.sh config_ds.yml
```

| Layout | 13.7K prefill | 64K prefill | Decode |
|---|---|---|---|
| **5 GPUs, 72 experts on CPU** | **1,259 T/s** | **1,187 to 1,417 T/s** | 61 / 59 / 76 T/s |
| 4 GPUs `[70,24,24,24,0]`, 112 experts | 1,133 to 1,212 T/s | 1,054 to 1,352 T/s | 65 / 60 / 73 T/s |
| Before tuning (stock engine, old hardware) | about 805 T/s | | about 50 / 44 / 57 T/s (other prompts) |

The 4-GPU layout keeps only one card on USB4; use it if the USB4 link is unreliable (see below).
The 64K figure varies more from run to run because DeepSeek's n-gram table is read from disk.

#### GLM-5.3-Flash 4.1bpw

```yaml
gpu_split: [68,24,24,24,24]
cpu_moe_split_experts: 32
cpu_moe_threads: 14
chunk_size: 4096
draft_mode: mtp
draft_num_tokens: 2
```

```sh
CUDA_DEVICE_ORDER=PCI_BUS_ID ./start.sh config_glm_4.1bpw.yml
```

| Experts on CPU, chunk size | 12.6K prefill | 59K prefill | Decode |
|---|---|---|---|
| **32, 4096** | **1,200 T/s** | **1,545 T/s** | 62 / 60 / 67 T/s |
| 36, 4096 | 1,169 T/s | 1,521 T/s | 60 / 60 / 68 T/s |
| 28, 2048 | 1,172 T/s | 1,262 T/s | 66 / 61 / 69 T/s |
| 48, 2048 (previous config) | 884 T/s | 981 T/s | 57 / 58 / 66 T/s |

28 experts with chunk 4096 and 24 with chunk 2048 do not fit.

### What did not help

| Tried | Result |
|---|---|
| Chunk 2048 instead of 4096 | 10% to 30% slower prefill |
| More experts on the CPU to free VRAM | Slower prefill and decode at every step up |
| Fewer layers on GPU 0 | Slower in every layout tried |
| Adding a slow card (RTX 4060 Ti) as an extra stage | Slower prefill and decode |
| Three or more host cores | Same as two |
| Hand-tuned `EXL3_MOE_STREAM_T` | 1% to 3%, within run-to-run noise |
| Prefill depth 3 | About 3% more prefill, but no VRAM to spare on GPU 0 |

### USB4 eGPU enclosures

Twice, under sustained load with both USB4 cards busy, one enclosure's link dropped
(`pciehp: Link Down`, `thunderbolt: device disconnected`, then NVIDIA `Xid 79, GPU has fallen
off the bus`). The driver then flags every GPU as needing a reboot (`Xid 154`), and reloading the
driver does not recover it: processes stuck in the driver keep it loaded. Both drops happened
with the two enclosures on one shared smart plug. On separate plugs, over an hour and a half of
5-GPU load (including a 60-minute soak) ran without an event. That suggests the shared plug
played a part, though one clean run does not prove it.

A drop leaves little evidence on its own, so log while testing:

```sh
nvidia-smi --query-gpu=timestamp,index,temperature.gpu,power.draw.instant,clocks.sm,utilization.gpu,clocks_event_reasons.active \
  --format=csv -lms 500 >> gpu_log.csv &
journalctl -kf | grep --line-buffered -iE "xid|pciehp|thunderbolt" >> kernel_log.txt &
```

If an enclosure disconnects, power-cycle only that enclosure (not a shared plug), then reboot.

### Checking a setup

- **Topology and link speed.** `nvidia-smi topo -m` and `lspci -tv` show where each card sits;
  reported link widths alone can hide a USB4 tunnel or a shared chipset uplink. Measure actual
  host-to-GPU bandwidth with a pinned-memory copy if the numbers matter.
- **Is the pipeline helping?** Compare prefill speed with `EXL3_DS_PIPELINE=0`.
- **Is the host CPU-starved?** `top -H -p <server pid>` during a long prefill. If the stage threads
  together use most of the cores the server is pinned to, try `EXL3_MOE_HOST_CORES=2`.
- **Deterministic comparisons.** MoE offload is not bit-reproducible by default. For exact
  A/B checks of engine changes, set `EXL3_MOE_CPU_PROMOTE=0 EXL3_MOE_CPU_SWAP=0
  EXL3_MOE_RECON_DET=1 EXL3_MOE_STREAM_FUSED_T=0`. These freeze expert placement and make the
  offloaded experts' accumulation order fixed, at no measurable speed cost.
