## Performance Tuning: Multi-GPU with CPU MoE Offload

This page collects what was measured while tuning large MoE models (DeepSeek-V4.1-Flash and
GLM-5.3-Flash) on a mixed multi-GPU machine with part of each MoE layer offloaded to the CPU.
The general guidance applies to similar setups; the numbers at the end are from one machine and
are there as a worked example, not as targets.

Measured on 2026-11-17 with ExLlamaV3 1.6.7 plus the pipelined prefill patch described below.
Updated on 2026-11-18: the host-core results were remeasured with expert placement held fixed
(see [The saved expert profile](#the-saved-expert-profile)), and the patch's default pipeline depth
was raised (see Pipeline depth below).

### Pipelined prefill with CPU offload (patched ExLlamaV3)

Stock ExLlamaV3 runs prefill as a pipeline across GPUs (each GPU works on a different chunk at
the same time), but it falls back to serial prefill whenever experts are offloaded to the CPU or
attention is pinned to one device (DeepSeek-V4 does this). The `master` branch of the ExLlamaV3
fork at <https://github.com/duyyudus/exllamav3> lifts both restrictions. It is a
small patch on top of ExLlamaV3 1.6.7. Measured gains over serial prefill with 2 chunks in
flight:

| Model | Prefill speedup |
|---|---|
| DeepSeek-V4.1-Flash (attention pinned to GPU 0, CPU offload) | about 1.25x to 1.5x |
| GLM-5.3-Flash 4.1bpw (CPU offload) | about 1.7x to 1.8x |

Models with neither CPU offload nor pinned attention take the stock code path unchanged.

**Pipeline depth.** The number of chunks in flight decides how many GPUs can work at once. The
first version of the patch capped it at 2, so on five GPUs at most two were busy and each sat idle
most of the time waiting for a slot. The patch now keeps the stock limit (number of devices + 1)
by default, which made GLM prefill 26% (13K) to 37% (60K) faster for about 100 MiB more VRAM. With
a pinned attention device, every chunk in flight also allocates on that one device for each of its
layers (about 0.3 GiB per chunk on DeepSeek), so the default there stays at 2;
`EXL3_DS_PIPELINE_DEPTH` overrides it (see the DeepSeek setup below).

The fork's commit for this also fixes a timing dependence: each GPU's expert-streaming threshold
comes from a bandwidth probe, which used to run while other GPUs streamed over shared links, so the
threshold, and with it the rounding of the output, could change from run to run. All GPUs are now
probed one after another before any streaming starts.

Output was compared bit for bit against serial prefill (single requests, cached-prefix reuse,
checkpoint resume and two concurrent requests) on both models, and again at every depth used here
(GLM at 2, 3, 4, 5, 6 and the default; DeepSeek at 3). Decode speed is unchanged.

The patch only speeds up prefill while nothing else is decoding: the generator flushes the
pipeline before every decode step, so with several requests at once, a prompt that arrives while
another request is generating prefills at serial speed. That is correct, just not faster.

**Using the fork.** Clone it (the patch is on `master`), then point `developer.exllamav3_path` at
the clone in the configs that should use it:

```sh
git clone https://github.com/duyyudus/exllamav3 ~/git/exllamav3
```

```yaml
developer:
  exllamav3_path: ~/git/exllamav3
```

The same option is available on the command line as `--exllamav3-path ~/git/exllamav3`. Configs
without it use the installed package, so the patch is switched per config, and removing the line
switches it off. The startup log shows `Using exllamav3 from <path>` when it is active.

Only the Python package is loaded from the clone; the compiled extension still comes from the
installed ExLlamaV3 wheel, so no build is needed. That also means the clone must stay on the same
release as the installed wheel and must not change C++/CUDA code. After merging a newer upstream
release into the fork, update the installed wheel to the same version.

| Variable | Default | Effect |
|---|---|---|
| `EXL3_DS_PIPELINE` | `1` | `0` restores the stock rule (serial prefill with CPU offload) |
| `EXL3_DS_PIPELINE_DEPTH` | `0` | Cap on chunks in flight. `0`: devices + 1, or 2 with a pinned attention device |
| `EXL3_DS_PIPELINE_MIN_ROWS` | `256` | Shorter chunks run serially |

### Environment variables

These cannot be set in `config.yml`; put them in front of the launch command.

| Variable | Recommended | Why |
|---|---|---|
| `CUDA_DEVICE_ORDER` | `PCI_BUS_ID` | Always, with mixed GPUs. See below |
| `EXL3_MOE_HOST_CORES` | `2` for DeepSeek, unset (1) for GLM | Physical cores reserved for the server process. 2% or less either way |
| `EXL3_DS_PIPELINE_DEPTH` | `3` for DeepSeek with the layout below, unset for GLM | GLM's default already keeps every GPU busy; DeepSeek's default is 2, and 3 needs room on GPU 0 |
| `EXL3_MOE_STREAM_T` | unset | Leave the per-GPU automatic value |

**`CUDA_DEVICE_ORDER=PCI_BUS_ID`.** By default CUDA numbers GPUs fastest first, not in the order
`nvidia-smi` shows. `gpu_split` (and any autosplit) follows CUDA's numbering, so adding or
swapping a card can silently move the budgets to different GPUs. On the machine below, adding an
RTX 4090 made it GPU 0 ahead of the RTX PRO 5000, which would have given the 70 GB budget to
a 24 GB card. With `PCI_BUS_ID`, the numbering matches `nvidia-smi`.

**`EXL3_MOE_HOST_CORES`.** With CPU offload, ExLlamaV3 pins the server process to this many
physical cores (default 1, i.e. two logical CPUs) and gives the rest to the expert worker. With
expert placement held fixed, 2 host cores gave about 2% more prefill on DeepSeek and about 1% on
GLM, with decode unchanged. An earlier measurement of +10% to 25% on DeepSeek and -22% to 32% on
GLM was wrong: the expert profile changed between those runs. More than 2 gave nothing further.
Keep `cpu_moe_threads` at or below physical cores minus host cores (14 on a 16-core CPU with 2 host
cores); with more worker threads, the host gets fewer cores than requested. tabbyAPI sizes its
torch thread cap from this variable automatically.

The host is not what limits prefill. During a long prefill, each GPU's host thread waits for work
57% to 87% of the time, and a thread holds the Python GIL in only about 23% of samples. Most of
the remaining time is spent waiting for the GPU at two device-to-host copies per MoE layer. CUDA
spin-waits there by default, so `top` shows the server's threads using nearly all of their pinned
cores (189% of 200% on GLM) even though they are idle. With sleeping waits instead, server CPU fell
to 16% (GLM) and 30% (DeepSeek) at unchanged prefill and decode speed. A faster host or
host-side code changes would therefore not speed up prefill.

**`EXL3_MOE_STREAM_T`.** During prefill, CPU-held experts that enough tokens use are streamed to
the GPU and the rest are computed on the CPU. The engine picks this cut-off per GPU from its
measured link speed (about 8 on a Gen5 x8 link up to about 20 on a 3.8 GB/s link). Setting the
variable replaces that with one value for every GPU. Hand-tuned per-GPU values were at most 1% to
3% better on the current hardware, so it is not worth changing.

### Config settings

**`gpu_split`.** Budgets in GB per GPU, in `CUDA_DEVICE_ORDER=PCI_BUS_ID` order. Put the largest
card first: GPU 0 holds the first pipeline stage and, for DeepSeek, every layer's attention and
the n-gram layers. At 2 chunks in flight, moving layers off GPU 0 (smaller GPU 0 budget, more on
other cards) was slower in every layout tried. Leave GPU 0 room beyond what the load reports: on
DeepSeek, prefill needs about 2 GiB there at depth 2 and about 0.3 GiB more per extra chunk, which
is why its config uses 68 rather than 70 (see the DeepSeek setup below).

**`cpu_moe_split_experts`.** Use the lowest value that loads. Fewer experts on the CPU means
less to stream per chunk, so prefill improves at every step down. Decode gains little, because
decode is limited mostly by host overhead. A value too low fails at load with
`Insufficient VRAM in split for model and cache`.

**`chunk_size`.** 4096 was 10% to 30% faster than 2048 for prefill, because streaming the CPU
experts costs about the same per chunk whatever its size. Larger chunks did not fit: at load the
engine reserves one full chunk's working memory on every GPU, so 6144 or 8192 left too little
room for the layers on 24 GB cards.

**`draft_mode: mtp`.** Faster decode on both models. Draft settings were measured on 5 GPUs with
one user: five prompt types (code, explanation, list, rewriting given code, story) at 700 tokens
each, greedy and with the config's sampling preset. The same setting run twice differed by up to
3%.

| Model and setting | Greedy decode | Sampled decode |
|---|---|---|
| GLM, `draft_num_tokens: 1` | 58.0 T/s | 56.3 T/s |
| GLM, `draft_num_tokens: 2` (two runs) | 61.4 to 62.0 T/s | 60.2 to 62.0 T/s |
| GLM, `draft_num_tokens: 3` (blank) | 62.5 T/s | 60.4 T/s |
| GLM, `draft_num_tokens: 4` | 60.2 T/s | 55.5 T/s |
| **GLM, `dynamic_draft: true`, ceiling 3** | **64.8 T/s** | **62.2 T/s** |
| GLM, `dynamic_draft: true`, ceiling 4 | 64.5 T/s | 62.4 T/s |
| **DeepSeek, defaults (two runs)** | **62.6 to 64.2 T/s** | **61.0 to 62.0 T/s** |
| DeepSeek, `dynamic_draft: true` | 64.4 T/s | 61.8 T/s |
| DeepSeek, `draft_num_tokens: 3` / `4` | 61.9 / 63.7 T/s | 60.6 / 60.4 T/s |
| DeepSeek, `EXL3_DSPARK_CONF=0.3` / `0.7` | 62.8 / 58.4 T/s | 59.4 / 58.3 T/s |

For GLM, use `dynamic_draft: true` and leave `draft_num_tokens` blank (3 is the ceiling). Each
extra drafted position is accepted less often, and with experts on the CPU a rejected position
still costs a full verification row, so fixed lengths peak at 2 to 3. `dynamic_draft` drops a
position when the drafter's calibrated confidence predicts a rejection, keeping about the
acceptance of 2 with the tokens per step of 3.

For DeepSeek, leave both blank. Its drafter drafts a block of 5 and already cuts it with its own
confidence head (`EXL3_DSPARK_CONF`, default 0.5). It does not report the confidence values
`dynamic_draft` uses, so that setting has no effect; the difference above is within noise.
Capping the block or moving the confidence cut-off was no faster.

**`max_batch_size`.** 1 for a single user. 2 works correctly with the patch, but the extra cache
needs VRAM that GPU 0 barely has on DeepSeek.

### The saved expert profile

With CPU offload, ExLlamaV3 keeps a per-model record of how often each expert is routed, in
`~/.cache/exllamav3/expert_stats/` (one JSON file per model; each records its `model_dir`). At
load, the most-used experts go to the GPUs and the rest to the CPU, and during a session experts
the CPU had to compute are moved into spare GPU slots. At shutdown the file is overwritten with
the session's counts. Those counts decay by 2% per step, so the file mostly reflects the last few
hundred steps before shutdown. A 60K-token prefill is only about 15 steps (one per chunk), while
400 decoded tokens are about 170, so a session that ends with chat leaves a decode-shaped profile.

That placement matters. GLM with the same config, each profile built in its own session on text
the benchmark does not use (the benchmark prompts are Python source; its generations are chat
answers):

| Profile at load | 13K prefill | 60K prefill | Decode |
|---|---|---|---|
| Built from long prompts only (other Python code) | 1,448 T/s | 1,994 T/s | 57 T/s |
| Agent-like: long code prompt plus an answer, four times | 1,394 T/s | 1,915 T/s | 60 T/s |
| 50/50 blend of the first and last rows | 1,305 T/s | 1,797 T/s | 65 T/s |
| Built from chat answers only | 1,200 T/s | 1,586 T/s | 68 T/s |

What decides it is the kind of text, not prefill versus decode. The two code-built profiles put
73% of the same experts on the CPU; a code-built and a chat-built profile share only 21% to 26%.
GLM's answers open with reasoning prose, so chat generation favours different experts than long
code prompts, and with 32 of 288 experts per layer on the CPU the GPUs cannot hold both sets.
There is no setting that wins both ways; there is a trade-off to choose.

By default the profile follows whatever the last session did, so a consistent workload converges on
its own. To pin a compromise instead, average two saved profiles (normalise each layer's counts,
then take the mean) and load the result with `EXL3_MOE_CPU_SPLIT_STATS`, as below. In-session
promotion still adjusts from there.

**Comparing settings.** Each run rewrites the profile the next run starts from, so a sequence of
A/B runs drifts. Hold placement fixed by giving every run the same copy of the profile:

```sh
python3 -c "import json,sys; json.dump(json.load(open(sys.argv[1]))['layers'], open(sys.argv[2], 'w'))" \
  ~/.cache/exllamav3/expert_stats/<file>.json frozen_profile.json
EXL3_MOE_CPU_SPLIT_STATS=$PWD/frozen_profile.json ./start.sh <config>
```

The engine still overwrites its own profile at shutdown, but loads from the frozen file. Repeat
the baseline at the end of a sweep to see the run-to-run noise (here about 1% for prefill and 3 T/s
for decode).

### Measured setups

Hardware: Ryzen 9 7950X (16 cores), 122 GB RAM, five GPUs. Each GPU's PCIe link decides how fast
CPU-held experts reach it during prefill.

| GPU (PCI order) | Card | Connection | Host to GPU |
|---|---|---|---|
| 0 | RTX PRO 5000 72 GB | CPU lanes, Gen5 x8 | 28.9 GB/s |
| 1 | RTX 4090 24 GB | CPU lanes, Gen4 x8 | 13.4 GB/s |
| 2 | RTX 3090 24 GB | chipset, Gen4 x4 | 6.4 GB/s |
| 3 | RTX 3090 24 GB | USB4 enclosure | 3.8 GB/s (3.3 when both USB4 cards are busy) |
| 4 | RTX 3090 24 GB | USB4 enclosure | 3.8 GB/s (3.3 when both USB4 cards are busy) |

Both configs below also set `developer.exllamav3_path` to the patched fork.

Benchmarks are uncached prompts of about 13K and 60K tokens, then three 500 to 600 token greedy
generations. During a long run the engine moves frequently used experts into spare VRAM, so
sustained prefill on repeated content climbed to about 1,400 T/s (13K) and 1,900 T/s (60K) on
GLM. Real, varied use lands between the cold numbers below and those.

The tables below were measured before the expert profile was held fixed (see
[The saved expert profile](#the-saved-expert-profile)), so differences of a few percent between
rows may come from expert placement rather than the setting. The large effects (chunk size, the
number of experts on the CPU, the pipelined prefill patch) are well outside that.

#### DeepSeek-V4.1-Flash 2.68bpw

```yaml
gpu_split: [68,24,24,24,24]
cpu_moe_split_experts: 76
cpu_moe_threads: 14
chunk_size: 4096
draft_mode: mtp
```

```sh
CUDA_DEVICE_ORDER=PCI_BUS_ID EXL3_MOE_HOST_CORES=2 EXL3_DS_PIPELINE_DEPTH=3 ./start.sh config_ds.yml
```

DeepSeek runs every layer's attention on GPU 0, so each prefill chunk in flight needs working
memory there: about 2 GiB beyond the loaded model at depth 2, and about 0.3 GiB more per extra
chunk. With `[70,…]` and 72 experts on the CPU, depth 3 runs out of memory on GPU 0. Moving one
layer off GPU 0 (68, with 76 experts on the CPU so the other cards still fit) makes room for 3:

| Layout, depth (frozen expert profile, 2026-11-18) | 13.7K prefill | 64K prefill | GPU 0 peak |
|---|---|---|---|
| `[70,…]`, 72 experts, depth 2 (previous config) | 1,204 T/s | 1,121 to 1,343 T/s | 71.0 GiB |
| `[68,…]`, 76 experts, depth 2 | 1,177 T/s | 1,113 to 1,315 T/s | 70.1 GiB |
| **`[68,…]`, 76 experts, depth 3** | **1,252 T/s** | **1,235 to 1,522 T/s** | **70.5 GiB** |
| `[68,…]`, 76 experts, depth 4 | 1,259 T/s | 1,230 to 1,459 T/s | 70.7 GiB |

Depth 3 is about 4% (13K) to 12% (64K) faster than the previous config and leaves more room on GPU
0: 0.7 GiB under the 71.2 GiB that PyTorch can use there, against 0.2 GiB before. Decode was
unchanged (62 to 68 T/s across these runs). The gain is smaller than GLM's because GPU 0 runs
attention for every layer, which limits how much the other GPUs can overlap. The 64K figure varies
more from run to run because DeepSeek's n-gram table is read from disk.

Earlier layouts, at depth 2 (2026-11-17, expert profile not held fixed):

| Layout | 13.7K prefill | 64K prefill | Decode |
|---|---|---|---|
| 5 GPUs `[70,…]`, 72 experts on CPU | 1,259 T/s | 1,187 to 1,417 T/s | 61 / 59 / 76 T/s |
| 4 GPUs `[70,24,24,24,0]`, 112 experts | 1,133 to 1,212 T/s | 1,054 to 1,352 T/s | 65 / 60 / 73 T/s |
| Before tuning (stock engine, old hardware) | about 805 T/s | | about 50 / 44 / 57 T/s (other prompts) |

The 4-GPU layout keeps only one card on USB4; give the 0 to whichever card should be left out.

### What did not help

| Tried | Result |
|---|---|
| Chunk 2048 instead of 4096 | 10% to 30% slower prefill |
| More experts on the CPU to free VRAM | Slower prefill and decode at every step up |
| Fewer layers on GPU 0, at 2 chunks in flight | Slower in every layout tried (on DeepSeek at depth 3, one layer fewer is what makes room) |
| Adding a slow card (RTX 4060 Ti) as an extra stage | Slower prefill and decode |
| Two or more host cores | 2% or less |
| Sleeping instead of spinning CUDA waits | Same speed; server CPU 189% to 16% (no tabbyAPI option yet) |
| Hand-tuned `EXL3_MOE_STREAM_T` | 1% to 3%, within run-to-run noise |
| DeepSeek pipeline depth 4 instead of 3 | No faster; GPU 0, which runs all attention, is the limit |

### USB4 eGPU enclosures

Three times, under sustained load with both USB4 cards busy, one enclosure's link dropped
(`pciehp: Link Down`, `thunderbolt: device disconnected`, then NVIDIA `Xid 79, GPU has fallen
off the bus`). The driver then flags every GPU as needing a reboot (`Xid 154`), and reloading the
driver does not recover it: processes stuck in the driver keep it loaded.

It was the same enclosure every time (GPU 3), and the cause was most likely its power: the
enclosures were on smart plugs (first one shared, later one each), and the plug had a loose
contact. With both enclosures on plain wall sockets, over three hours of near-continuous 5-GPU load
ran without a drop. (Brief instantaneous readings of 330 to 370 W, above the 300 W limit, show on
every card under pipelined prefill; they were not the cause.) Power eGPU enclosures directly, not
through smart plugs or worn power strips.

If drops come back with direct power:

- Swap the two enclosures' cables and host ports. If the drops follow the enclosure, the fault is
  in the enclosure.
- Cap the USB4 cards' clocks or power (`nvidia-smi -i <gpu> -lgc 0,<MHz>` or `-pl <W>`) to soften
  the load spikes. Those stages are not the bottleneck, so the cost should be small.
- Run without the failing card by setting its `gpu_split` entry to 0 and raising
  `cpu_moe_split_experts` until the model loads (112 for DeepSeek on four cards).

A drop leaves little evidence on its own, so log while testing:

```sh
nvidia-smi --query-gpu=timestamp,index,temperature.gpu,power.draw.instant,clocks.sm,utilization.gpu,clocks_event_reasons.active \
  --format=csv -lms 500 >> gpu_log.csv &
journalctl -kf | grep --line-buffered -iE "xid|pciehp|thunderbolt" >> kernel_log.txt &
```

If an enclosure disconnects, power-cycle only that enclosure (not a shared plug), then reboot.

### Checking a setup

- **Topology and link speed.** `nvidia-smi topo -m` and `lspci -tv` show where each card sits;
  reported link widths alone can hide a USB4 tunnel or a shared chipset uplink. Measure actual
  host-to-GPU bandwidth with a pinned-memory copy if the numbers matter.
- **Is the pipeline helping?** Compare prefill speed with `EXL3_DS_PIPELINE=0`.
- **High server CPU use is not starvation.** With CPU offload the server's threads spin while they
  wait for the GPU, so `top -H` shows them near 100% while they are effectively idle. To check
  whether more host cores help, compare `EXL3_MOE_HOST_CORES=1` and `2` with a frozen expert
  profile instead.
- **Comparing settings.** Freeze the expert profile for every run (see
  [The saved expert profile](#the-saved-expert-profile)) and repeat the baseline at the end.
- **Deterministic comparisons.** MoE offload is not bit-reproducible by default. For exact
  A/B checks of engine changes, set `EXL3_MOE_CPU_PROMOTE=0 EXL3_MOE_CPU_SWAP=0
  EXL3_MOE_RECON_DET=1 EXL3_MOE_STREAM_FUSED_T=0`. These freeze expert placement and make the
  offloaded experts' accumulation order fixed, at no measurable speed cost. Comparing across server
  sessions, also set `EXL3_MOE_STREAM_T` (any value): the automatic per-GPU value comes from a
  timed bandwidth probe, and a reading near a rounding boundary (3.81 GB/s gives 20, 3.78 gives 21)
  changes which experts are streamed and so the rounding of the output.
