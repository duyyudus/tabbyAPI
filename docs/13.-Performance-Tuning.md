## Performance Tuning: Multi-GPU with CPU MoE Offload

This page collects what was measured while tuning large MoE models (DeepSeek-V4.1-Flash and
GLM-5.3-Flash) on a mixed multi-GPU machine with part of each MoE layer offloaded to the CPU.
The general guidance applies to similar setups; the numbers at the end are from one machine and
are there as a worked example, not as targets.

Measured on 2026-11-17 with ExLlamaV3 1.6.7 plus the pipelined prefill patch described below.
Updated on 2026-11-18: the host-core results were remeasured with expert placement held fixed
(see [The saved expert profile](#the-saved-expert-profile)), and the patch's default pipeline depth
was raised (see Pipeline depth below). Updated on 2026-11-20: faster decode kernels in the fork,
which now needs its extension built (see [Using the fork](#using-the-fork)), a breakdown of
[where decode time goes](#where-decode-time-goes), scheduling for
[concurrent requests](#concurrent-requests), host cores remeasured at the current pipeline
depth, which makes 2 the setting for GLM as well (see
[Environment variables](#environment-variables)),
[copying CPU experts ahead](#copying-cpu-experts-ahead-patched-exllamav3) during prefill, and fixes
for DeepSeek's
[shared attention device](#deepseek-sharing-the-attention-device-patched-exllamav3). Updated on
2026-11-21: DeepSeek now runs 4 chunks in flight (see
[the DeepSeek setup](#deepseek-v41-flash-268bpw)) and keeps each attention layer on its own GPU
(see [DeepSeek: attention on every GPU](#deepseek-attention-on-every-gpu-patched-exllamav3)).

### Pipelined prefill with CPU offload (patched ExLlamaV3)

Stock ExLlamaV3 runs prefill as a pipeline across GPUs (each GPU works on a different chunk at
the same time), but it falls back to serial prefill whenever experts are offloaded to the CPU or
attention is pinned to one device (DeepSeek-V4 does this). The `master` branch of the ExLlamaV3
fork at <https://github.com/duyyudus/exllamav3> lifts both restrictions. It is a
small patch on top of ExLlamaV3 1.6.7. Measured gains over serial prefill with 2 chunks in
flight:

| Model | Prefill speedup |
|---|---|
| DeepSeek-V4.1-Flash (attention pinned to GPU 0, CPU offload) | about 1.25x to 1.5x |
| GLM-5.3-Flash 4.1bpw (CPU offload) | about 1.7x to 1.8x |

Models with neither CPU offload nor pinned attention take the stock code path unchanged.

**Pipeline depth.** The number of chunks in flight decides how many GPUs can work at once. The
first version of the patch capped it at 2, so on five GPUs at most two were busy and each sat idle
most of the time waiting for a slot. The patch now keeps the stock limit (number of devices + 1)
by default, which made GLM prefill 26% (13K) to 37% (60K) faster for about 100 MiB more VRAM. With
a pinned attention device, every chunk in flight also allocates on that one device for each of its
layers (about 0.3 GiB per chunk on DeepSeek), so the default there stays at 2;
`EXL3_DS_PIPELINE_DEPTH` overrides it (see the DeepSeek setup below).

The fork's commit for this also fixes a timing dependence: each GPU's expert-streaming threshold
comes from a bandwidth probe, which used to run while other GPUs streamed over shared links, so the
threshold, and with it the rounding of the output, could change from run to run. All GPUs are now
probed one after another before any streaming starts.

Output was compared bit for bit against serial prefill (single requests, cached-prefix reuse,
checkpoint resume and two concurrent requests) on both models, and again at every depth used here
(GLM at 2, 3, 4, 5, 6 and the default; DeepSeek at 3 and 4). Decode speed is unchanged.

The patch only speeds up prefill while nothing else is decoding: the generator flushes the
pipeline before every decode step, so with several requests at once, a prompt that arrives while
another request is generating prefills at serial speed. `prefill_priority` pauses the generating
requests instead, so the prompt keeps the pipeline (see
[Concurrent requests](#concurrent-requests)).

The patch is Python only, so it works with or without building the fork's extension (see
[Using the fork](#using-the-fork)).

| Variable | Default | Effect |
|---|---|---|
| `EXL3_DS_PIPELINE` | `1` | `0` restores the stock rule (serial prefill with CPU offload) |
| `EXL3_DS_PIPELINE_DEPTH` | `0` | Cap on chunks in flight. `0`: devices + 1, or 2 with a pinned attention device |
| `EXL3_DS_PIPELINE_MIN_ROWS` | `256` | Shorter chunks run serially |

### Copying CPU experts ahead (patched ExLlamaV3)

With the pipeline full, GLM's prefill speed is set by GPU 0: it holds 22 of the 45 layers and is
busy for the whole prefill, while the other GPUs have time to spare. During prefill, the
CPU-held experts that enough tokens use are copied to the GPU and computed there. Stock code
computes each copied batch as soon as it lands, before the experts already on the GPU, so the GPU
waited on every copy: GPU 0 spent about 14% of its time copying with nothing else to do.

The fork's `master` can reserve a buffer on a GPU for those copies (`EXL3_MOE_STREAM_AHEAD_MB`).
The copies start as soon as a layer's routing is known, the experts already on the GPU are
computed next, and the copied experts after them, so the copies overlap that work. On GPU 0 the
time spent only copying fell from 14% to 3%. Which experts are copied, the batches and the order
of the sums are unchanged, so the output is identical: greedy text and the top logprobs matched
the previous code on both models, on long, cached-reuse and short prompts. A 10-minute soak under
production load (four clients mixing long prompts, cached follow-ups and decodes) ran without
errors, and the model found a passphrase hidden in each of 32 long prompts.

Measured within one server session each, switching it at runtime, with 2 host cores and expert
placement held fixed:

| Buffer on GPU 0 | 13K prefill | 60K prefill | Decode | VRAM on GPU 0 |
|---|---|---|---|---|
| GLM, 416 MB | +3% | +6% between decode rounds, +11% in a prefill-only session | unchanged | +0.4 GB |
| DeepSeek, 384 MB | +1.7% | +1.3% | unchanged | +0.4 GB |

DeepSeek gains little because its GPU 0 also runs every layer's attention, so the copies are a
small part of its time; its config leaves the buffer off, since GPU 0 has little room to spare. A
buffer for all of a layer's copied experts (544 MB on GLM) was no faster than 416 MB: what matters
is that the first batches are in place when the GPU gets to them. Decode never takes this path.
With the buffer on, GLM's pipeline is close to balanced: the two USB4-attached GPUs are now about
as busy as GPU 0.

Use it on the GPU with the fastest host link, GPU 0 on this layout. On a slow link, the CPU's
share of the experts would start later than before.

| Variable | Default | Effect |
|---|---|---|
| `EXL3_MOE_STREAM_AHEAD_MB` | unset (off) | Buffer per GPU as `<CUDA index>:<MB>[,...]`, e.g. `0:416`. Counts against that GPU's budget at load |
| `EXL3_MOE_STREAM_AHEAD` | `1` | `0` turns it off in a running server (the buffer stays allocated). Read per layer, for A/B tests |

### DeepSeek: sharing the attention device (patched ExLlamaV3)

DeepSeek runs every layer's attention on GPU 0, so during a pipelined prefill each other GPU sends
its activations to GPU 0 for every layer's attention and gets the result back. Profiling showed
that this, not the GPUs' own work, set DeepSeek's prefill speed: the USB4-attached GPU 3 took
about 1.9 s per 4096-token chunk against about 1 s on GPU 0, and sat idle 74% of that time. Two
things held it up:

- **The lock on GPU 0.** Each GPU's thread takes one lock to launch work on GPU 0, and GPU 0's
  own thread takes it once per layer. Python's lock lets a thread that releases it take it straight
  back, so GPU 0's thread ran a whole chunk's layers while the others waited, about 145 ms per
  attention call on average and up to a second.
- **The copies.** Without peer access between the cards, each copy between two GPUs is staged
  through host memory by the driver and blocks the source GPU's stream for the whole transfer:
  returning an 84 MB attention result to a USB4 card held GPU 0's only stream for 26 ms.

The fork's `master` fixes both, each behind its own switch:

- `EXL3_DS_FAIR_LOCK=1` hands the lock to waiting threads in arrival order.
- `EXL3_DS_ATTN_STAGE=1` moves the attention input and output through pinned host buffers. The slow
  hops run on the calling GPU's own stream, the input is sent before the lock is taken, and GPU 0
  only does its fast hops while holding it.

Measured within one server session, switching at runtime (production config, depth 3, 2 host
cores, expert placement held fixed):

| Setting | 13K prefill | 64K prefill | Decode |
|---|---|---|---|
| Both off | 1,303 T/s | 1,568 T/s | 73.4 T/s |
| Fair lock | 1,512 T/s (+16%) | 1,709 T/s (+9%) | 74.5 T/s |
| Staged copies | 1,354 T/s (+4%) | 1,611 T/s (+3%) | 73.5 T/s |
| **Both** | **1,596 T/s (+22%)** | **1,981 T/s (+26%)** | 71.3 T/s |

In a fresh session with both on, 64K prefill ran at about 1,800 T/s against 1,504 without them.
GPU 3's time per chunk roughly halved (about 2.4 to 1.3 s), and GPU 0's rose (about 1.1 to 1.4 s),
since it now takes the other GPUs' attention calls in turn: DeepSeek's pipeline is close to
balanced, and a fourth chunk in flight now pays off (see
[the DeepSeek setup](#deepseek-v41-flash-268bpw)). Decode does not take this path; its differences
above are noise between rounds.

Neither uses VRAM; the staged copies take about 192 MiB of pinned host RAM per GPU (the 80 and
40 MiB buffers, rounded up to powers of two by PyTorch's pinned allocator). The output is
identical: greedy text and the top logprobs matched the previous code on long, cached-reuse and
short prompts, and again with two prompts' chunks in the pipeline at once (two long prompts sent
together, and a short prompt arriving during a long one's prefill). A 10-minute soak under
production load ran without errors, and the model found a passphrase hidden in each of 27 long
prompts. Models without a pinned attention device, such as GLM, take the unchanged code path.

| Variable | Default | Effect |
|---|---|---|
| `EXL3_DS_FAIR_LOCK` | `0` | `1`: the attention device's lock goes to waiting threads in arrival order. Read at every acquisition |
| `EXL3_DS_ATTN_STAGE` | `0` | `1`: remote attention input and output go through pinned host buffers. Read at every call |

### DeepSeek: attention on every GPU (patched ExLlamaV3)

The fixes above make the shared attention device faster, but GPU 0 still runs its own 21 layers
plus the attention of the 19 layers on the other cards, and each of those layers still sends its
activations to GPU 0 and back (about 126 MB per 4096-token chunk). Attention is pinned because of
how DeepSeek-V4.1 is built: its layers attend over caches that earlier layers wrote. Layers 20 to
39 all read layer 20's cache, and a few layers choose which cache entries the next ones attend to.
ExLlamaV3 keeps every attention layer on one GPU so that those caches exist once.

The fork's `master` adds another way, selected with the model option `attn_device: local`
(ExLlamaV3's `Model.load(attn_device = "local")`). Each attention layer stays on its own layer's
GPU, and each GPU that reads a shared cache keeps a copy of it. The rows each forward pass adds to
the cache, the entry choices and the candidate blocks go to those GPUs through pinned host memory:
a few MB per GPU per chunk instead of 126 MB per layer. Measured in alternating server sessions
(production config, depth 4, two sessions each, 2026-11-21):

| Attention | 13K prefill | 64K prefill | 488K prefill | Decode | Decode step |
|---|---|---|---|---|---|
| Pinned to GPU 0 | 1,615 T/s | 2,130 T/s | 1,465 T/s | 74.6 T/s | 31.7 ms |
| **On every GPU** | **1,783 T/s (+10%)** | **2,442 T/s (+15%)** | **2,050 T/s (+40%)** | 72.5 T/s | 31.6 ms |

Every 64K round on every GPU was faster than every pinned one. The gain grows with prompt length,
because attention costs more per token on a longer prompt, and pinned, all of that lands on GPU 0,
the stage that sets the pace (the 488K figures are one prompt per mode). GPU 0 is still that
stage, now about 85% busy, while the other cards are 42% to 66% busy. A decode step takes the same
time; the lower decode speed comes from slightly fewer draft tokens accepted on the two test
prompts.

The output is close to pinned but not identical, since attention now runs on other GPU models,
which round differently: the top three tokens agreed on every test prompt, and greedy text
matched for 24 tokens on four of five. Within this mode the output is fixed: repeated sessions,
cached prefixes, two prompts' chunks in the pipeline at once, cache defragmentation, and restores
from the host-RAM and disk cache tiers all gave identical results. A 20-minute soak under
production load ran without errors, with the passphrase found in all 60 long prompts.

The copies take VRAM on the 24 GB cards: at the 524,288-token cache, layer 20's cache alone is
640 MiB on each GPU that reads it. The layout therefore needs 88 experts on the CPU instead of 76,
and GPU 3's budget at 22 moves one of its layers to GPU 4 (see
[the DeepSeek setup](#deepseek-v41-flash-268bpw)). Long prompts need the most room: an early version
kept the candidate blocks as a mask that grows with the prompt (about 240 MB per chunk at 470K)
and ran out of memory on a 488K-token prompt at 88 experts. The fork now sends them as fixed-size
indices, and at 488K the fullest card had about 290 MiB free. Pinned attention is as tight there:
GPU 0 had 124 MiB free on the same prompt.

Models without shared caches, one GPU and tensor parallelism take the unchanged code paths. The
fair lock and staged copies have no effect in this mode, since no GPU is shared.

### Faster decode kernels (patched ExLlamaV3)

At decode, each MoE layer's routed experts run in fused kernels that handle up to 8 rows: one row
per decoded token, or the few rows of a draft verification. Profiling them showed they were limited
by memory latency, not by arithmetic: every slice of weights waited for a full round trip to
memory before its first multiply. The fork's `master` rewrites them:

- Each warp streams its weight slices through a shared-memory ring with asynchronous copies, so
  waits only cover loads issued several slices earlier.
- Gate/up and down run as one persistent launch whose blocks take work from a queue, instead of
  two launches.
- DeepSeek's 2.5-bit layers get a dedicated unpack, which needs fewer instructions per weight.

Measured in production mode with the expert profile frozen: 3 prompts x 400 greedy tokens with the
configs' drafting, kernels switched between requests within one server session (DeepSeek sessions
vary by 5% to 10% between server starts, so only comparisons within a session are reliable):

| Step | GLM-5.3-Flash 4.1bpw | DeepSeek-V4.1-Flash 2.68bpw |
|---|---|---|
| Original kernels to the slice ring and fused launch | 69.6 to 72.5 T/s (+4.1%) | 93.4 to 104.6 T/s (+12.0%) |
| Then the 2.5-bit unpack (a later session) | 72.5 to 72.6 T/s (+0.2%) | 104.8 to 108.4 T/s (+3.4%) |

Together that is about +4% on GLM and +16% on DeepSeek. These runs warm the server up first and
use their own prompts, so their absolute numbers are higher than the decode columns under
[Measured setups](#measured-setups), which predate these kernels. DeepSeek gains more because its
2.5 and 3-bit experts were the least efficient (36% to 50% of memory bandwidth on the RTX 3090s and
the PRO 5000) and its verify steps carry more rows. GLM's 4-bit experts were already closer to
bandwidth, and the expert kernels are only part of its step (see
[Where decode time goes](#where-decode-time-goes)).

The output is bit-identical to the original kernels. This was checked kernel by kernel on RTX 30xx,
RTX 40xx and RTX PRO 5000 cards for every bit width these models use, with greedy end-to-end
output on both models, with 20 to 30 minute soak runs under production load, and with a race test
that ran over 100,000 launches next to competing GPU work.

`EXL3_MOE_COOP_VARIANT` selects the kernels: `5` (default) is everything above, `4` the first
version (slice ring and fused launch only), `0` the original kernels. It is read at every launch,
so A/B tests can switch it in a running server. The fork's `doc/env_vars.md` has the details.

### Using the fork

Clone the fork, build its compiled extension in place, then point `developer.exllamav3_path` at
the clone in the configs that should use it:

```sh
git clone https://github.com/duyyudus/exllamav3 ~/git/exllamav3
cd ~/git/exllamav3
PYTHON=/path/to/tabbyAPI/venv/bin/python util/setup_toolchain_for_exl3_ext.sh   # once
PYTHON=/path/to/tabbyAPI/venv/bin/python util/build_exl3_ext.sh
```

```yaml
developer:
  exllamav3_path: ~/git/exllamav3
```

`PYTHON` is the interpreter tabbyAPI runs with, because the extension is compiled against its torch.
The setup script creates a private CUDA 12.8.1 and gcc-11 toolchain in `~/toolchains` without root
or touching the system (Ubuntu or Debian; about 30 seconds plus downloads; its header lists the
requirements). The build takes about 5 minutes and writes `exllamav3_ext*.so` into the clone. Run
it while no model is loaded: the compiler jobs need tens of GB of RAM. It builds for RTX 30xx, RTX
40xx and RTX 50xx / PRO Blackwell cards by default; set `TORCH_CUDA_ARCH_LIST` for others.

The same option is available on the command line as `--exllamav3-path ~/git/exllamav3`. Configs
without it use the installed package, so the fork is switched per config, and removing the line
switches it off. When it is active, the startup log shows two lines:

```
Using exllamav3 from /home/<user>/git/exllamav3/exllamav3
Using exllamav3_ext from /home/<user>/git/exllamav3/exllamav3_ext.cpython-312-x86_64-linux-gnu.so
```

If the second line points into the installed package instead, the clone has no build. The Python
code (and with it pipelined prefill) still loads from the clone, but the decode kernels are the
original ones from the installed wheel, and the clone must then stay on the wheel's release.
With a build, rebuild after pulling changes to the fork's C++/CUDA code and after upgrading torch.
Deleting the `.so` falls back to the installed wheel.

### Environment variables

These cannot be set in `config.yml`; put them in front of the launch command.

| Variable | Recommended | Why |
|---|---|---|
| `CUDA_DEVICE_ORDER` | `PCI_BUS_ID` | Always, with mixed GPUs. See below |
| `EXL3_MOE_HOST_CORES` | `2` | Physical cores reserved for the server process. GLM's 60K prefill about 5% faster than at 1; 3 gave nothing further on either model |
| `EXL3_DS_PIPELINE_DEPTH` | `4` for DeepSeek with the layout below, unset for GLM | GLM's default already keeps GPU 0, the stage that sets the pace, busy throughout; DeepSeek's default is 2, and at 4 GPU 0, which runs every layer's attention, is busy throughout (5 is no faster) |
| `EXL3_MOE_STREAM_AHEAD_MB` | `0:416` for GLM, unset for DeepSeek | Copy-ahead buffer on GPU 0, see [Copying CPU experts ahead](#copying-cpu-experts-ahead-patched-exllamav3) |
| `EXL3_DS_FAIR_LOCK`, `EXL3_DS_ATTN_STAGE` | `1` for DeepSeek, unset for GLM | DeepSeek prefill 22% to 26% faster with pinned attention, see [DeepSeek: sharing the attention device](#deepseek-sharing-the-attention-device-patched-exllamav3); no effect without a pinned attention device, so none with `attn_device: local` |
| `EXL3_MOE_STREAM_T` | unset | Leave the per-GPU automatic value |

**`CUDA_DEVICE_ORDER=PCI_BUS_ID`.** By default CUDA numbers GPUs fastest first, not in the order
`nvidia-smi` shows. `gpu_split` (and any autosplit) follows CUDA's numbering, so adding or
swapping a card can silently move the budgets to different GPUs. On the machine below, adding an
RTX 4090 made it GPU 0 ahead of the RTX PRO 5000, which would have given the 70 GB budget to
a 24 GB card. With `PCI_BUS_ID`, the numbering matches `nvidia-smi`.

**`EXL3_MOE_HOST_CORES`.** With CPU offload, ExLlamaV3 pins the server process to this many
physical cores (default 1, i.e. two logical CPUs) and gives the rest to the expert worker. Use 2
for both models. Each GPU has a host thread in the server process, and at the default pipeline
depth they all work through a long prefill at the same time. On one core they queue for the CPU:
during a 60K GLM prefill, GPU 0's thread was ready to run but waiting for a CPU 27% of the time.
That thread sets the pace, because GPU 0 holds 22 of GLM's 45 layers and is busy for the whole
prefill while the other GPUs have time to spare.

Each comparison below alternated the settings in one running server (re-pinning it between
rounds), with expert placement held fixed. The first round of each session was left out, because
expert placement and DeepSeek's n-gram reads settle during it.

| Model, comparison | 13K prefill | 60K prefill | Decode |
|---|---|---|---|
| GLM, 1 to 2 host cores | 1,629 to 1,637 T/s | 2,504 to 2,634 T/s (+5%) | 66.6 to 67.3 T/s |
| GLM, 2 to 3 host cores (13 worker threads) | 1,643 to 1,656 T/s | 2,627 to 2,639 T/s | 71.0 to 69.9 T/s |
| DeepSeek at depth 3, 2 to 3 host cores (13 worker threads) | 1,318 to 1,319 T/s | 1,588 to 1,592 T/s | 75.7 to 75.7 T/s |

Separate sessions for 1 and 2 host cores gave +6.5% on GLM's 60K prefill. A 13K prompt is only
about 3 chunks, so the pipeline never fills and the threads do not crowd the core. With 2 chunks
in flight, 2 host cores gave only about 1% on GLM, which is why earlier versions of this page left
GLM at 1. An earlier measurement of +10% to 25% on DeepSeek and -22% to 32% on GLM was wrong: the
expert profile changed between those runs.

Keep `cpu_moe_threads` at or below physical cores minus host cores (14 on a 16-core CPU with 2 host
cores); with more worker threads, the host gets fewer cores than requested. With 14 worker threads
on 16 cores, the second host core sits unused at the default of 1, so 2 costs nothing. A third
needs a worker thread fewer and gave nothing. tabbyAPI sizes its torch thread cap from this
variable automatically.

A thread holds the Python GIL in under 10% of samples, so the GIL is not a limit. With 2 host
cores and sleeping waits, GPU 0 still sat idle about 12% of each chunk, mostly on queued work: the
hand-off of each chunk to the next GPU, expert-promotion bookkeeping, and the CPU experts' worker.
Those need engine changes. CUDA spin-waits for the GPU by default, so `top` shows the server's
threads using nearly all of their pinned cores (189% of 200% on GLM) even when they are only
waiting. With sleeping waits instead, server CPU fell to 16% (GLM) and 30% (DeepSeek) at 2 chunks
in flight. At the default depth with 1 host core, sleeping waits made GLM's 60K prefill 5.8%
faster, because spinning threads no longer crowded the core; with 2 host cores they add about
0.6%, within noise.

**`EXL3_MOE_STREAM_T`.** During prefill, CPU-held experts that enough tokens use are streamed to
the GPU and the rest are computed on the CPU. The engine picks this cut-off per GPU from its
measured link speed (about 8 on a Gen5 x8 link up to about 20 on a 3.8 GB/s link). Setting the
variable replaces that with one value for every GPU. Hand-tuned per-GPU values were at most 1% to
3% better on the current hardware, so it is not worth changing.

### Config settings

**`gpu_split`.** Budgets in GB per GPU, in `CUDA_DEVICE_ORDER=PCI_BUS_ID` order. Put the largest
card first: GPU 0 holds the first pipeline stage and, for DeepSeek, every layer's attention and
the n-gram layers. At 2 chunks in flight, moving layers off GPU 0 (smaller GPU 0 budget, more on
other cards) was slower in every layout tried. Leave GPU 0 room beyond what the load reports: on
DeepSeek, prefill needs about 2 GiB there at depth 2 and about 0.3 GiB more per extra chunk, which
is why its config uses 68 rather than 70 (see the DeepSeek setup below).

**`cpu_moe_split_experts`.** Use the lowest value that loads. Fewer experts on the CPU means
less to stream per chunk, so prefill improves at every step down. Decode gains little: waiting for
CPU experts costs about 2 ms of a decode step of over 40 ms (see
[Where decode time goes](#where-decode-time-goes)). A value too low fails at load with
`Insufficient VRAM in split for model and cache`.

**`chunk_size`.** 4096 was 10% to 30% faster than 2048 for prefill, because streaming the CPU
experts costs about the same per chunk whatever its size. Larger chunks did not fit: at load the
engine reserves one full chunk's working memory on every GPU, so 6144 or 8192 left too little
room for the layers on 24 GB cards.

**`draft_mode: mtp`.** Faster decode on both models. Draft settings were measured on 5 GPUs with
one user: five prompt types (code, explanation, list, rewriting given code, story) at 700 tokens
each, greedy and with the config's sampling preset. The same setting run twice differed by up to
3%.

| Model and setting | Greedy decode | Sampled decode |
|---|---|---|
| GLM, `draft_num_tokens: 1` | 58.0 T/s | 56.3 T/s |
| GLM, `draft_num_tokens: 2` (two runs) | 61.4 to 62.0 T/s | 60.2 to 62.0 T/s |
| GLM, `draft_num_tokens: 3` (blank) | 62.5 T/s | 60.4 T/s |
| GLM, `draft_num_tokens: 4` | 60.2 T/s | 55.5 T/s |
| **GLM, `dynamic_draft: true`, ceiling 3** | **64.8 T/s** | **62.2 T/s** |
| GLM, `dynamic_draft: true`, ceiling 4 | 64.5 T/s | 62.4 T/s |
| **DeepSeek, defaults (two runs)** | **62.6 to 64.2 T/s** | **61.0 to 62.0 T/s** |
| DeepSeek, `dynamic_draft: true` | 64.4 T/s | 61.8 T/s |
| DeepSeek, `draft_num_tokens: 3` / `4` | 61.9 / 63.7 T/s | 60.6 / 60.4 T/s |
| DeepSeek, `EXL3_DSPARK_CONF=0.3` / `0.7` | 62.8 / 58.4 T/s | 59.4 / 58.3 T/s |

For GLM, use `dynamic_draft: true` and leave `draft_num_tokens` blank (3 is the ceiling). Each
extra drafted position is accepted less often, and with experts on the CPU a rejected position
still costs a full verification row, so fixed lengths peak at 2 to 3. `dynamic_draft` drops a
position when the drafter's calibrated confidence predicts a rejection, keeping about the
acceptance of 2 with the tokens per step of 3.

For DeepSeek, leave both blank. Its drafter drafts a block of 5 and already cuts it with its own
confidence head (`EXL3_DSPARK_CONF`, default 0.5). It does not report the confidence values
`dynamic_draft` uses, so that setting has no effect; the difference above is within noise.
Capping the block or moving the confidence cut-off was no faster.

**`max_batch_size`.** 4, with `prefill_priority` on (see
[Concurrent requests](#concurrent-requests)). One user runs exactly as at 1: same tokens, same
speed, and 0.1 to 0.3 GB more VRAM (GPU 0 on DeepSeek peaked at 72.2 GB against 72.0 GB at 1).
Without `prefill_priority`, keep it at 1.

### The saved expert profile

With CPU offload, ExLlamaV3 keeps a per-model record of how often each expert is routed, in
`~/.cache/exllamav3/expert_stats/` (one JSON file per model; each records its `model_dir`). At
load, the most-used experts go to the GPUs and the rest to the CPU, and during a session experts
the CPU had to compute are moved into spare GPU slots. At shutdown the file is overwritten with
the session's counts. Those counts decay by 2% per step, so the file mostly reflects the last few
hundred steps before shutdown. A 60K-token prefill is only about 15 steps (one per chunk), while
400 decoded tokens are about 170, so a session that ends with chat leaves a decode-shaped profile.

That placement matters. GLM with the same config, each profile built in its own session on text
the benchmark does not use (the benchmark prompts are Python source; its generations are chat
answers):

| Profile at load | 13K prefill | 60K prefill | Decode |
|---|---|---|---|
| Built from long prompts only (other Python code) | 1,448 T/s | 1,994 T/s | 57 T/s |
| Agent-like: long code prompt plus an answer, four times | 1,394 T/s | 1,915 T/s | 60 T/s |
| 50/50 blend of the first and last rows | 1,305 T/s | 1,797 T/s | 65 T/s |
| Built from chat answers only | 1,200 T/s | 1,586 T/s | 68 T/s |

What decides it is the kind of text, not prefill versus decode. The two code-built profiles put
73% of the same experts on the CPU; a code-built and a chat-built profile share only 21% to 26%.
GLM's answers open with reasoning prose, so chat generation favours different experts than long
code prompts, and with 32 of 288 experts per layer on the CPU the GPUs cannot hold both sets.
There is no setting that wins both ways; there is a trade-off to choose.

By default the profile follows whatever the last session did, so a consistent workload converges on
its own. To pin a compromise instead, average two saved profiles (normalise each layer's counts,
then take the mean) and load the result with `EXL3_MOE_CPU_SPLIT_STATS`, as below. In-session
promotion still adjusts from there.

**Comparing settings.** Each run rewrites the profile the next run starts from, so a sequence of
A/B runs drifts. Hold placement fixed by giving every run the same copy of the profile:

```sh
python3 -c "import json,sys; json.dump(json.load(open(sys.argv[1]))['layers'], open(sys.argv[2], 'w'))" \
  ~/.cache/exllamav3/expert_stats/<file>.json frozen_profile.json
EXL3_MOE_CPU_SPLIT_STATS=$PWD/frozen_profile.json ./start.sh <config>
```

The engine still overwrites its own profile at shutdown, but loads from the frozen file. Repeat
the baseline at the end of a sweep to see the run-to-run noise (here about 1% for prefill and 3 T/s
for decode).

### Where decode time goes

With drafting on, each decode step drafts a few tokens and then verifies them in one forward pass
of the full model, accepting about 3 tokens per step on both models. With the faster kernels, a GLM
step takes about 44 ms: 38 ms verifying and 6 ms drafting. DeepSeek splits its step the same way,
about 86% verifying and 14% drafting. The layers are split across the GPUs, so during verification
the cards take turns: GPU 0 on GLM is busy for 14.5 ms of the 38, all of it while its own layers
run. During drafting, no GPU runs a kernel for 2.3 to 3.8 ms per step. That is not the embedding
lookups, although both drafters' tables are in system RAM: having GPU 0 read GLM's table directly,
with no round trip to the host, shortened drafting by only about 0.1 ms per step. Each draft pass
waits on the one before it and on hops between GPUs: GLM's drafter layer runs on GPU 0 and its
output layer on GPU 4, and without peer access each hop is staged through host memory. Waiting for
CPU-held experts costs about 2 ms per step.

On GLM, some GPU is busy for most of the step. Per token, the expert kernels take about 5 ms of GPU
time and attention about 4 ms (at roughly 70% of memory bandwidth); the hundreds of small per-layer
kernels add up to under 1 ms. DeepSeek's GPUs wait more: GPU 0 runs every layer's attention, so
each layer copies its activations there and back, and those copies and the CPU experts left all
GPUs idle at once for about 28% of the step before the new kernels.

For scale: reading every weight once per step at each card's measured bandwidth would allow about
140 T/s on GLM and 200 T/s on DeepSeek at this acceptance rate, against the 73 and 108 T/s measured.
DeepSeek's figure is out of reach anyway: at 2.5 bits its expert kernels are limited by the
arithmetic of unpacking weights on the RTX 3090s, not by bandwidth. The rest of the gap is spread
over kernels running below full bandwidth, the drafting phase, and waits for the host, CPU experts
and cross-GPU copies. No single part of it was large enough to win back more than a few percent;
see the decode rows below.

### Concurrent requests

When a prompt arrives while another request is generating, stock ExLlamaV3 feeds it in 2048-token
slices, one every fifth decode step, so the request already streaming keeps going. That suits
models that run entirely on GPUs, where a slice takes a fraction of a second. With experts on the
CPU, a slice runs without the prefill pipeline (it is flushed before every decode step) and takes
about 2.5 s against about 45 ms per decode step, so both requests slow down about threefold.

The fork's `prefill_priority` option (in tabbyAPI's `model` section) replaces that rule:

- While any prompt has chunks left, generating requests pause, so the prompt keeps the pipeline
  full and prefills at its full speed.
- Prompts go in one at a time, the one with the fewest uncached tokens first, instead of a slice
  each in turn.
- A request whose prompt is done gets its first token before the next prompt continues.
- With `prefill_slice`, paused requests get a turn of `decode_slice` seconds after that long. The
  pause also includes finishing the chunks already in flight.

| Setting | Value | Why |
|---|---|---|
| `max_batch_size` | `4` | Up to four requests are served at once instead of queueing behind each other |
| `prefill_priority` | `true` | The stock rule is slower for every request with CPU offload |
| `prefill_slice` / `decode_slice` | `8` / `2.0` | Caps a stream's pause at about 11 s when a long prompt arrives |
| `draft_max_rows` (`draft_model` section) | `8` | The full draft window for one or two requests, 1 token for three or four |

With the option off, the engine takes the stock path, and configs on the installed package
(without `developer.exllamav3_path`) ignore it with a warning. Leave it off for models that run
entirely on GPUs.

**A prompt arriving during a stream.** Request D streams 1000 tokens; 1.5 s later, request E
sends a 35K (GLM) or 38K (DeepSeek) token prompt. `max_batch_size: 2`, mean of two runs; E's
first token is counted from its arrival. D alone takes 15.8 s (GLM) and 11.4 s (DeepSeek); E alone
gets its first token in 14 s on GLM. These runs held expert promotion off, so absolute speeds are
below production; the comparisons hold.

| Rule | GLM: D done | GLM: E first token | DeepSeek: D done | DeepSeek: E first token | D's longest pause |
|---|---|---|---|---|---|
| Stock | 54.0 s | 43.0 s | 65.0 s | 57.0 s | 2.5 to 3 s, every few steps |
| `prefill_priority` | 30.3 s | 14.6 s | 39.7 s | 27.5 s | 13 s (GLM), 26 s (DeepSeek) |
| ...with 8 s / 2 s turns | 30.7 s | 18.9 s | 44.4 s | 36.1 s | 10.4 s (GLM), 11.6 s (DeepSeek) |

Two ~55K prompts sent together both got their first token after 38.5 s (GLM) and 78 s (DeepSeek)
under the stock rule; with `prefill_priority`, the first after 21 and 40 s, the second after 40 and
78 s. A 2K prompt arriving behind a ~55K one got its first token after 12 s instead of 17 s (GLM)
and 21 s instead of 30 s (DeepSeek). It cannot overtake the long prompt's chunks already in the
pipeline.

**More requests at once.** Four clients, each sending a ~20K-token slice of a codebase and then
two follow-ups on the cached prefix, 400 tokens per answer, each client sending its next turn as
soon as the last one ends. DeepSeek in production mode (expert promotion on, after a warm-up), mean
of two rounds:

| `max_batch_size` | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| All 12 answers done | 119 s | 120 s | 122 s | 124 s |
| First token of a follow-up turn (2nd / 3rd) | 37 / 16 s | 22 / 11 s | 10 / 5 s | 1.3 / 1.3 s |
| First token of a first turn | 42 s | 41 s | 40 s | 41 s |
| Speed of each stream | 82 T/s | 34 T/s | 23 T/s | 19 T/s |
| Longest pause in a stream | 1 s | 13 s | 13 s | 14 s |

Total throughput hardly changes: one prompt already keeps the GPUs busy, and decoding several
requests at once gains little. What changes is who waits. At 1, a client's next turn queues behind
the other clients' whole answers. At 4 it starts at once, while every stream runs slower and pauses
whenever another client's prompt goes in. First turns wait about as long at any setting, because
four large prompts arriving together go in one after another. GLM (with promotion off) showed the
same pattern; all answers were done 13% sooner at 4 (101 s against 116 s).

Decoding alone, with no prompts arriving, four requests together give about 1.2 times the
throughput of running them one after another on DeepSeek (1.5 to 1.7 on GLM) with a 1-token
draft window, but only 1.03 times with the full window. That is what `draft_max_rows: 8` is for.

**Output.** A request's greedy output can differ from what the same request produces alone,
under the stock rule as well, because a batch changes the rounding of the forward pass. In
DeepSeek tests, outputs parted at tokens where the model was undecided: its top choice had a median
probability of 0.39 (never above 0.58), with the second close behind. Quality is unaffected; one
request at a time gives the same tokens at any `max_batch_size`.

### USB4 eGPU enclosures

Three times, under sustained load with both USB4 cards busy, one enclosure's link dropped
(`pciehp: Link Down`, `thunderbolt: device disconnected`, then NVIDIA `Xid 79, GPU has fallen
off the bus`). The driver then flags every GPU as needing a reboot (`Xid 154`), and reloading the
driver does not recover it: processes stuck in the driver keep it loaded.

It was the same enclosure every time (GPU 3), and the cause was most likely its power: the
enclosures were on smart plugs (first one shared, later one each), and the plug had a loose
contact. With both enclosures on plain wall sockets, over three hours of near-continuous 5-GPU load
ran without a drop. (Brief instantaneous readings of 330 to 370 W, above the 300 W limit, show on
every card under pipelined prefill; they were not the cause.) Power eGPU enclosures directly, not
through smart plugs or worn power strips.

If drops come back with direct power:

- Swap the two enclosures' cables and host ports. If the drops follow the enclosure, the fault is
  in the enclosure.
- Cap the USB4 cards' clocks or power (`nvidia-smi -i <gpu> -lgc 0,<MHz>` or `-pl <W>`) to soften
  the load spikes. This costs some prefill on GLM, whose later stages are 85% to 91% busy in a long
  prefill: 250 W on GPUs 1, 2 and 4 made it 3% to 4% slower. DeepSeek was unaffected.
- Run without the failing card by setting its `gpu_split` entry to 0 and raising
  `cpu_moe_split_experts` until the model loads (112 for DeepSeek on four cards).

A drop leaves little evidence on its own, so log while testing:

```sh
nvidia-smi --query-gpu=timestamp,index,temperature.gpu,power.draw.instant,clocks.sm,utilization.gpu,clocks_event_reasons.active \
  --format=csv -lms 500 >> gpu_log.csv &
journalctl -kf | grep --line-buffered -iE "xid|pciehp|thunderbolt" >> kernel_log.txt &
```

If an enclosure disconnects, power-cycle only that enclosure (not a shared plug), then reboot.

### Checking a setup

- **Topology and link speed.** `nvidia-smi topo -m` and `lspci -tv` show where each card sits;
  reported link widths alone can hide a USB4 tunnel or a shared chipset uplink. Measure actual
  host-to-GPU bandwidth with a pinned-memory copy if the numbers matter.
- **Is the pipeline helping?** Compare prefill speed with `EXL3_DS_PIPELINE=0`.
- **Is copy-ahead on?** The startup log shows `-- CPU MoE stream copy-ahead ring: cuda:0 416 MB`,
  followed by a note of how many of a layer's batches fit.
- **Is DeepSeek's attention on every GPU?** The startup log shows `Keeping each attention layer on
  its own layer's GPU (attn_device: local).`
- **Are the faster decode kernels active?** The startup line `Using exllamav3_ext from` must point
  into the fork's clone (see [Using the fork](#using-the-fork)). To measure them, compare
  `EXL3_MOE_COOP_VARIANT=0` and the default within one server session.
- **High server CPU use alone does not show starvation.** With CPU offload the server's threads
  spin while they wait for the GPU, so `top -H` shows them near 100% even when they are only
  waiting. Starvation shows as time spent runnable but not running: the second field of
  `/proc/<pid>/task/<tid>/schedstat`, in nanoseconds, read before and after a long prefill. To
  check whether more host cores help, compare `EXL3_MOE_HOST_CORES` values with a frozen expert
  profile.
- **Comparing settings.** Freeze the expert profile for every run (see
  [The saved expert profile](#the-saved-expert-profile)) and repeat the baseline at the end.
- **Deterministic comparisons.** MoE offload is not bit-reproducible by default. For exact
  A/B checks of engine changes, set `EXL3_MOE_CPU_PROMOTE=0 EXL3_MOE_CPU_SWAP=0
  EXL3_MOE_RECON_DET=1 EXL3_MOE_STREAM_FUSED_T=0`. These freeze expert placement and make the
  offloaded experts' accumulation order fixed, at no measurable speed cost. Comparing across server
  sessions, also set `EXL3_MOE_STREAM_T` (any value): the automatic per-GPU value comes from a
  timed bandwidth probe, and a reading near a rounding boundary (3.81 GB/s gives 20, 3.78 gives 21)
  changes which experts are streamed and so the rounding of the output.
